\chapter{Implementation}\label{s:implementation}

This chapter details how the design decisions of Chapter~\ref{s:design} are
realised in code. It follows the same component breakdown introduced in
Chapter~\ref{s:overview}.

\section{Pipeline Orchestrator}

The orchestrator (\texttt{src/pipeline.py}) implements \texttt{run\_pipeline()},
which loops over the generation--validation--execution cycle described in
Chapter~\ref{s:overview} for at most \texttt{MAX\_RETRIES}~$=3$ attempts. Before
attempting generation, it queries the semantic cache
(Section~\ref{s:cache-impl}) for the intent and returns the cached script and
result immediately on a hit; on a miss, it decomposes the intent into
sub-tasks via \texttt{IntentDecomposer} (\texttt{src/intent\_decomposer.py})
before retrieval, exactly as the other two entry points do. Key
functions include \texttt{check\_syntax()}, a fast local heuristic check
(balanced braces/parentheses, correct \texttt{let}-binding syntax) that
rejects obviously malformed output before Brane is ever invoked, and returns
a boolean success flag with a diagnostic message; \texttt{check\_semantic()}, which validates function and
argument usage against the retrieved package context before execution is
attempted; and \texttt{execute\_workflow()}, which submits the candidate
workflow to the Brane runtime --- which compiles and executes it as a single
\texttt{brane workflow run} command --- and captures \texttt{stdout},
\texttt{stderr}, and the exit code, distinguishing a compilation failure from
a runtime failure. On success, the (intent, script, result) triple is
written back to the semantic cache. Ambiguous intents are detected via
\texttt{is\_clarification\_request()} and handled by
\texttt{ask\_for\_clarification()}, which returns a question to the user
instead of attempting generation. Successful workflows are persisted with
\texttt{save\_branescript\_to\_folder()} for later inspection and reuse as
training or cache-seeding data. \texttt{build\_pipeline\_components()}
initialises the embedding model
(\texttt{sentence-transformers/all-MiniLM-L6-v2}), the single
\texttt{PkgRetriever} instance shared across a pipeline run, and the
\texttt{SemanticCache} instance (constructed defensively: a failure to reach
the cache's ChromaDB collection is caught and logged, and the pipeline
proceeds with caching disabled rather than failing outright); the
BraneScript syntax reference is loaded once as plain text and requires no
embedding model at all. A \texttt{--no-cache} command-line flag allows the
cache to be bypassed explicitly for a given invocation.

\section{Knowledge Base and Retrieval}

\texttt{src/knowledgeBase.py} builds and queries the single vector store
introduced in Section~\ref{s:design}, \texttt{brane\_pkg\_db}. Package specifications
(\texttt{container.yml} files) are parsed and exploded into per-function
\texttt{Document} chunks, each annotated with the owning package name and a
short usage hint, and embedded via LangChain's \texttt{HuggingFaceEmbeddings}
wrapper around \texttt{all-MiniLM-L6-v2}. The \texttt{PACKAGE\_ALIASES}
dictionary maps domain vocabulary to package identifiers and is consulted
before falling back to similarity search, implementing the hybrid retrieval
strategy described in Chapter~\ref{s:design}. There is no separate store for
BraneScript syntax: \texttt{load\_system\_prompt()}
(\texttt{src/prompts.py}) reads \texttt{data/syntax\_reference.md} once and
formats it directly into the generation system prompt for every request.

\section{Brane Packages}

Seven packages are implemented under \texttt{packages/} as the evaluation
testbed for this thesis: \texttt{healthcare}, \texttt{genomics},
\texttt{epidemics}, \texttt{statistics}, \texttt{text\_analysis},
\texttt{data\_masking}, and \texttt{datetime}. Neither the pipeline nor the
retriever is specific to these seven: both operate against whatever typed
functions are published in the Brane package registry a given deployment is
configured against, and the testbed packages exist to provide a concrete,
end-to-end domain on which to train and evaluate the system, not to bound
its scope. Each package follows a common dispatch convention: the
container's entry point reads the invoked function name from
\texttt{sys.argv[1]} (declared in the package's \texttt{command.args}
specification), rather than relying on environment variables, and routes to
the corresponding Python function. Structured return values are serialised as
tagged class instances (\texttt{["ClassName", \{...\}]}), consistent with the
typed data representation decision in Chapter~\ref{s:design}. Package images
are built with \texttt{docker buildx build}, extending a common base image;
the standard \texttt{brane package build} command was found to break functions
that return an \texttt{IntermediateResult}, so the Docker-based build path is
used for all seven packages instead.

\section{Fine-Tuning Infrastructure}

\texttt{src/fine\_tuning/train.py} implements supervised fine-tuning (SFT) and
provisions Group Relative Policy Optimisation (GRPO) as a subsequent stage.
Default SFT hyperparameters are LoRA rank~16 (alpha~32), 3 epochs, batch
size~2 with gradient accumulation~4 (effective batch size~8), learning rate
$2\times10^{-4}$ with a cosine schedule, using 4-bit quantisation through
Unsloth where available, with a plain Hugging Face/PEFT fallback otherwise. A
\texttt{DataCollatorForCompletionOnlyLM}/\texttt{train\_on\_responses\_only()}
path implements the response-only loss masking described in
Chapter~\ref{s:design}. Training runs on Snellius H100 GPUs via
\texttt{sbatch\_finetune.sh}; a \texttt{MetricsCallback} logs loss, gradient
norm, learning rate, and epoch to
\texttt{outputs/metrics/\textit{model}\_training\_metrics.jsonl} after every
step, and \texttt{\_save\_training\_config()} records the full hyperparameter
set alongside the resulting adapter, so that multiple SFT runs against the
same base model remain distinguishable.

\texttt{src/fine\_tuning/evaluate.py} computes the three metrics used
throughout Chapter~\ref{s:evaluation}: \emph{compile rate} (the fraction of
generated scripts accepted by the Brane compiler), \emph{execution rate} (the
fraction that run to completion with exit code~0), and \emph{output match
rate} (the fraction of executed scripts, among those with a stored reference
output, whose \texttt{stdout} matches the reference exactly). Like the
command-line and dashboard entry points, it decomposes each intent into
sub-tasks before retrieval by default, via the same \texttt{IntentDecomposer}
built from the model already loaded for generation; a \texttt{--skip-decomposition}
flag disables this step so that its effect on the reported metrics can be
measured directly (Chapter~\ref{s:evaluation}). It deliberately never
consults the semantic cache, for the reason given in Chapter~\ref{s:design}:
a cache hit would let a previously generated correct answer masquerade as
freshly generated output, inflating the reported rates without reflecting
the model actually being evaluated. The script
embeds the corresponding \texttt{training\_config.json} into each evaluation
result file, which lets the dashboard (Section~\ref{ss:frontend}) distinguish
between multiple SFT runs of the same base model without additional
bookkeeping.

\section{Semantic Cache}\label{s:cache-impl}

\texttt{src/semantic\_cache.py} implements the \texttt{SemanticCache} class
described in Chapter~\ref{s:design}, backed by a ChromaDB collection
(\texttt{brane\_pkg\_db/intent\_cache}) with a default similarity threshold
\texttt{DEFAULT\_THRESHOLD}~$=0.92$. Its public interface consists of
\texttt{lookup(intent)} (cosine similarity search, returning the cached
BraneScript above threshold or \texttt{None}), \texttt{store(intent,
branescript)}, \texttt{invalidate(intent)} (removing stale entries matching an
intent), and \texttt{stats()}/\texttt{list\_entries()} for inspection. The
cache is seeded with all 584 unique training intents and their reference
BraneScript by \texttt{scripts/populate\_cache.py}, and is consulted before
any decomposition or retrieval work is done: by \texttt{run\_pipeline()} on
the command-line entry point, and by \texttt{generate\_single.py} on the
dashboard/Snellius path, so that a cache hit avoids model-loading and
inference cost entirely on either entry point, in line with the
progressive-trust ordering. \texttt{evaluate.py} is the one caller that
deliberately never touches the cache (Chapter~\ref{s:design}).

\subsection{Cache Evaluation Harness}

\texttt{scripts/generate\_paraphrases.py} produces semantically equivalent
rewordings of each training intent (three per intent, targeting 1974
paraphrases total) using an LLM (Qwen3.5-4B by default), via the
\texttt{sbatch\_paraphrase.sh} SLURM wrapper. \texttt{scripts/test\_cache\_lookup.py}
then benchmarks cache behaviour by seeding the cache with the original
intents and querying it with the paraphrases, reporting: \emph{hit rate} (the
fraction of paraphrases that retrieve any entry above threshold),
\emph{correct rate} (the fraction retrieving the exact reference script),
\emph{fuzzy correct rate} (the fraction retrieving a script with Jaccard
bigram similarity $\geq 0.95$ after whitespace/comment normalisation), and
\emph{false-positive rate} (the fraction of hits that return the wrong
script). Its \texttt{--sweep} mode evaluates eight thresholds
($0.80$--$0.98$); the implementation queries the cache once per paraphrase at
threshold $0$ and applies each candidate threshold as a post-hoc filter on the
returned similarity scores, reducing the sweep from $8 \times 1974 = 15{,}792$
ChromaDB queries to $1974$.

\section{Job Watcher}

\texttt{scripts/remote\_execution/local/job\_watcher.py} is a small polling
daemon, started and supervised by \texttt{start.sh} alongside the dashboard,
that runs wherever Brane itself is reachable --- typically the researcher's
own machine, rather than the Snellius compute node that ran generation.
It watches a job directory for BraneScript files written by
\texttt{generate\_single.py}, and for each pending job invokes
\texttt{subprocess.run(["brane", "workflow", "run", "a", path])}, the same
command used by the command-line entry point, so that the authority
determining whether a script executes correctly is identical regardless of
which entry point produced it. The resulting exit code is interpreted the
same way on both entry points --- $2$ for a compilation failure, $1$ for a
runtime failure, $0$ for success --- and, together with \texttt{stdout} and
\texttt{stderr}, is written back to the job's result file for the dashboard
to pick up and, on failure, feed back into the retry sequence shown in
Figure~\ref{fig:sequence-diagram}. Separating job watching from the
dashboard process itself keeps the dashboard's own responsibilities limited
to submission, polling, and presentation, and lets Brane execution happen on
whichever machine has network access to the target Brane instances, which
need not be the machine serving the dashboard.

\section{Dashboard}\label{ss:frontend}

The dashboard (\texttt{frontend/}, served by \texttt{server.py}) exposes five
tabs: \emph{Results} and \emph{Exec Results} (static views over prior
evaluation runs), \emph{Evaluation} (a model-comparison table with a modal
showing full training hyperparameters per model, reading the embedded
\texttt{training\_config}), \emph{Runs} (completed interactive generation
jobs), and \emph{Generate} (interactive pipeline invocation). The Generate tab
submits a SLURM job to Snellius over SSH for a user-supplied intent and
selected model, polling a file-based job queue for status
(Queued~$\rightarrow$~Generating~$\rightarrow$~Executing~$\rightarrow$~Done)
and rendering the resulting BraneScript, execution output, and any errors in a
job card. Failed attempts are automatically retried up to
\texttt{MAX\_GENERATE\_RETRIES}~$=3$ times: on failure, the previous script and
its error are written to a context file on Snellius and injected into the next
generation attempt's prompt by \texttt{generate\_single.py}, mirroring the
error-feedback design of the core pipeline (Chapter~\ref{s:design}) at the
level of the interactive dashboard. Cache inspection endpoints
(\texttt{/api/cache/stats}, \texttt{/api/cache/entries},
\texttt{/api/cache/invalidate}) expose the semantic cache's state directly to
the dashboard.

\section{Infrastructure}

A single entry-point script, \texttt{start.sh}, starts, restarts, and stops
the local services (job watcher and dashboard), writing PIDs to
\texttt{outputs/logs/} and performing a post-start health check. All run
artefacts are consolidated under \texttt{outputs/}, with dedicated
subdirectories for LoRA adapters and merged weights
(\texttt{outputs/models/}), evaluation results (\texttt{outputs/eval/}),
training metrics and plots (\texttt{outputs/metrics/}), figures
(\texttt{outputs/figures/}), pipeline results
(\texttt{outputs/pipeline/results/}), generated BraneScript
(\texttt{outputs/branescripts/}), and logs (\texttt{outputs/logs/}), replacing
an earlier, less structured \texttt{output\_snellius/} layout.
