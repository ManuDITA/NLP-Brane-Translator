\chapter{Overview}\label{s:overview}

This chapter presents the system built to address the problem stated in
Chapter~\ref{s:intro}: translating a natural-language scientific intent into a
correct, executable BraneScript workflow. We describe the system first from
the perspective of a user submitting an intent, and then show the resulting
architecture end to end; the design rationale behind these choices is
developed in Chapter~\ref{s:design}, and their implementation in
Chapter~\ref{s:implementation}.

\section{User Perspective}

A researcher interacts with the system by submitting a single natural-language
sentence, for example: \emph{``I want to analyse all heart-disease data using
package Healthcare''}. No knowledge of BraneScript syntax, package function
signatures, or Brane's execution model is required; the sentence is written
exactly as the researcher would describe the task to a colleague.

\paragraph{Entry points.} Two entry points expose this interaction, both
built around the same cache-lookup, decomposition, retrieval, and generation
steps (Section~\ref{s:pipeline-variants} and Chapter~\ref{s:implementation}
give the full detail), but aimed at different use cases:

\begin{itemize}
    \item \textbf{Command-line tool} (\texttt{src/pipeline.py}). Intended for
        local development, debugging, and batch experimentation, this entry
        point is invoked directly on a machine with the model loaded locally,
        either for a single intent or for a file of intents processed one
        after another. It runs synchronously to completion and additionally
        applies a local heuristic syntax/semantic pre-check to a generated
        script before optionally submitting it for execution.

    \item \textbf{Web dashboard} (\texttt{frontend/}, ``Generate'' tab). This
        is the entry point intended for interactive day-to-day use. The
        researcher types an intent and picks a model in the browser; the
        dashboard submits a batch job to the Snellius HPC cluster on a cache
        miss, polls for completion, and forwards the generated script and
        any compiler or runtime errors back to the researcher. On failure, it
        automatically resubmits the request with the error appended as
        corrective context, up to a fixed number of attempts, without the
        researcher having to intervene.
\end{itemize}

\paragraph{Outcomes.} Regardless of entry point, a submitted intent
eventually resolves to one of three outcomes:

\begin{enumerate}
    \item \textbf{Success.} A BraneScript workflow is generated, compiles,
        executes correctly on the Brane runtime, and its result (and, in the
        dashboard flow, the workflow itself) is returned to the researcher.
        The (intent, workflow, result) triple is also written to the
        semantic cache, so that a semantically equivalent future intent can
        be served immediately without invoking the model again.
    \item \textbf{Corrective retry.} Generation succeeds syntactically but the
        script fails to compile or fails at runtime against Brane. The
        compiler or runtime error is fed back into the prompt as corrective
        context and generation is retried, up to a fixed number of attempts
        (three, in the current configuration), before the researcher is shown
        anything.
    \item \textbf{Failure report.} All retries are exhausted without producing
        a working workflow. The researcher is shown the last generated
        script together with the error that caused it to fail, rather than a
        silent or generic error, so that the intent can be rephrased or the
        missing information (e.g., a dataset name) supplied explicitly.
\end{enumerate}

Figure~\ref{fig:sequence-diagram} traces the interactive (dashboard) case in
detail, showing the full sequence of messages between the researcher, the
dashboard, the semantic cache, the generation worker running on Snellius, and
the Brane runtime that ultimately compiles and executes the workflow.

\section{System Architecture}\label{s:pipeline-variants}

Figure~\ref{fig:pipeline-architecture} shows the conceptual, end-to-end
architecture shared by both entry points: an intent is checked against the
semantic cache; on a miss, it is decomposed into sub-tasks, used to retrieve
relevant package and dataset context, combined with a static BraneScript
syntax reference into a generation prompt, and passed to the LLM; the
resulting script is submitted to Brane, which authoritatively compiles and
executes it; and failures at either stage feed back into prompt construction
for a bounded number of retries.

Beyond generation, the two entry points diverge in one respect that matters
for how Chapter~\ref{s:evaluation}'s results should be read: only the
command-line tool applies the local heuristic pre-check
(Section~\ref{s:design-principles}) to a generated script before submitting
it for execution, while the dashboard/Snellius path submits every script
directly to Brane. The offline evaluation pipeline follows the same
decomposition and retrieval steps as both, but never consults the semantic
cache, so that its reported metrics are not inflated by cache hits
(Chapter~\ref{s:design} discusses the reasoning behind both choices).

Crucially, regardless of which package a workflow invokes, the data those
packages operate on never leaves the site at which it is registered:
the LLM only ever sees the natural-language intent, package function
signatures, and (redacted) dataset metadata during generation; the generated
BraneScript is executed by Brane's runtime against the dataset in place. This
separation between \emph{workflow generation} (which may involve cloud-hosted
or shared LLM infrastructure) and \emph{data access} (which remains local to
the owning site) is the architectural realisation of the privacy and
data-ownership motivation for choosing Brane as the target platform for this
work (Section~\ref{s:background}). Chapter~\ref{s:design} discusses the
rationale behind the choices summarised above, and Chapter~\ref{s:implementation}
describes how each component of Figures~\ref{fig:pipeline-architecture}
and~\ref{fig:sequence-diagram} is implemented.
